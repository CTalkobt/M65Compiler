# ln45 — Linker for .o45 Object Files

`ln45` links multiple `.o45` relocatable object files into a single flat binary or PRG executable. It resolves symbol references, merges segments, and applies relocations.

## Usage

```bash
ln45 [options] <file1.o45> [file2.o45 ...]
```

## Options

| Flag | Description |
|------|-------------|
| `-o <file>` | Output filename (default: `a.out`, or `a.prg` if `-prg`) |
| `-prg` | Output as PRG with 2-byte load address header (auto-detected from `.prg` extension) |
| `-basic` | Output as PRG with BASIC `SYS` stub at `$2001` (code starts at `$200D`; auto-run on MEGA65/C64) |
| `-t <addr>` | Set text segment base address (hex, default: `2000`) |
| `-d <addr>` | Set data segment base address (hex, default: after text) |
| `-b <addr>` | Set BSS segment base address (hex, default: after data) |
| `-z <addr>` | Set zero page base address (hex, default: `02`) |
| `-L <dir>` | Add a library search directory (also see `CC45_LIB` environment variable) |
| `-l <lib>` | Link against a `.lib` archive (selective linking — only needed members are pulled in) |
| `-m` | Print linker map (symbol addresses) after linking |
| `-M <file>` | Write detailed linker map file (segment layout, per-object contributions, symbols) |
| `--no-thunks` | Error on calling convention mismatches instead of generating thunks |
| `-Wthunk` | Warn on convention mismatches (default behavior — thunks are always warned) |
| `-V` / `--version` | Display version and exit |
| `-?` | Display help |

## Environment Variables

| Variable | Description |
|----------|-------------|
| `CC45_LIB` | Colon-separated list of directories to search for library files specified with `-l`. If a library path is not found as given, each directory in `CC45_LIB` is checked (followed by any `-L` directories). |

## Linking Process

The linker performs three passes:

### 1. Layout
Segments from all input objects are concatenated in input order:
- All text segments are merged into one contiguous text block
- All data segments are merged into one contiguous data block
- BSS and ZP lengths are summed
- Each object gets an offset within the merged segment

### 2. Symbol Resolution
- **Exports** from all objects are collected into a global symbol map
- Each export's final address is computed: `segment_base + object_offset + symbol_offset`
- **Imports** are verified — every imported symbol must have a matching export
- Duplicate exports are rejected with an error

### 3. Relocation
- Each object's relocation table is decoded
- For external references (`SEG_EXTERNAL`), the import name is looked up in the global symbol map
- For internal cross-segment references, the target segment's final base + object offset is computed
- The patched address is written into the merged segment body

## Relocation Types

| Type | Patch | Description |
|------|-------|-------------|
| `R_WORD` | 2 bytes | 16-bit absolute address |
| `R_LOW` | 1 byte | Low byte of 16-bit address |
| `R_HIGH` | 1 byte | High byte of 16-bit address |
| `R_LINEAR24` | 3 bytes | 24-bit linear address (MEGA65) |
| `R_LINEAR32` | 4 bytes | 32-bit linear address |
| `R_SEGADR` | 3 bytes | Segment address (bank:addr) |

## Examples

### Basic linking

```bash
# Compile two C files to objects
cc45 -c main.c -o main.o45
cc45 -c math.c -o math.o45

# Link into a PRG
ln45 -prg -o program.prg main.o45 math.o45
```

### Auto-running BASIC PRG (recommended for MEGA65/C64)

```bash
cc45 -c main.c -o main.o45

# Link with BASIC SYS stub — auto-runs on load
ln45 -basic -o program.prg main.o45 -l c45.lib
```

This produces a PRG that loads at `$2001` with a BASIC stub. Code starts at `$200D`. The program auto-runs when loaded via `LOAD"PROGRAM",8,1` then `RUN` (or auto-start).

### Assembly object linking

```bash
# Assemble to objects
ca45 -c main.s -o main.o45
ca45 -c utils.s -o utils.o45

# Link with explicit text base at $0800
ln45 -t 0800 -o program.bin main.o45 utils.o45
```

### Inspect before linking

```bash
# Check symbols
nm45 main.o45 utils.o45

# Link with map output
ln45 -prg -m -o program.prg main.o45 utils.o45
```

Example map output:
```
Symbol map:
  00002000 _main
  0000203c _add
  00002068 _mul2
  0000208b _result
```

### Detailed linker map file

```bash
ln45 -prg -M program.map -o program.prg main.o45 crt0.o45 puts.o45
```

Example map file (`program.map`):
```
Linker Map
==========

Memory Layout
-------------
  TEXT   $2000 - $203B  (60 bytes)
  DATA   $203C - $2041  (6 bytes)

Object Files
------------
  main.o45
    TEXT  $2000 - $2007  (8 bytes)
    DATA  $203C - $2041  (6 bytes)
  crt0.o45
    TEXT  $2008 - $200E  (7 bytes)
  puts.o45
    TEXT  $200F - $203B  (45 bytes)

Symbols (by address)
--------------------
  $2000  _main                          main.o45
  $2008  __init                         crt0.o45
  $200E  _init_features                 crt0.o45 [weak]
  $200F  _puts                          puts.o45
```

### Custom memory layout

```bash
ln45 -t 0800 -d 4000 -b 6000 -z 02 -o rom.bin boot.o45 kernel.o45
```

## Segment Addressing in Detail

The linker supports four primary memory segments, each placed independently:

### Text Segment (Code)
- Default: `$2000` (8192 decimal)
- Recommended range: `$0800` (MEGA65 BASIC end) to `$CFFF` (video memory start)
- Contains compiled code and readonly data
- Set with `-t <hex_address>`

**Example: ROM layout**
```bash
# Code starts at $E000 (60KB available for ROM code)
ln45 -t E000 -d F800 -o rom.bin kernel.o45 drivers.o45
```

### Data Segment (Initialized globals)
- Default: immediately after text
- Contains global variables with initializers
- Loaded with the program (included in `.prg` or binary)
- Set with `-d <hex_address>`

**Example: Split code and data**
```bash
# Code in RAM at $2000, data in bank 1 at $8000 (extended memory)
# (Requires MEGA65 extended banking support)
ln45 -t 2000 -d 8000 -o program.prg main.o45 -l c45.lib
```

### BSS Segment (Uninitialized globals)
- Default: immediately after data
- Contains zero-initialized globals (not in executable image)
- Must be zeroed at runtime (usually by `crt0`)
- Set with `-b <hex_address>`

**Example: Custom BSS region**
```bash
# Place BSS at $4000 (separate from code/data)
ln45 -t 2000 -d 3000 -b 4000 -o program.prg main.o45
```

### Zero Page Segment (8-bit addressing)
- Default: `$02` (start at byte 2; bytes 0-1 reserved for system)
- Contains fast-access globals and ZP temporaries
- Size limited by `$FF` (256 bytes total, minus OS reserves)
- Set with `-z <hex_address>`

**Example: Custom ZP allocation**
```bash
# Start ZP at $10 (skip $00-$0F for OS/system use)
ln45 -z 10 -o program.prg main.o45 -l c45_zp.lib
```

### Segment Layout Combinations

**Standard C program:**
```bash
ln45 -t 2000 -d 3000 -b 4000 -z 02 -o program.prg main.o45 -l c45.lib
# Result:
#   TEXT: $2000-$2FFF (code)
#   DATA: $3000-$3FFF (initialized globals)
#   BSS:  $4000-$4FFF (uninitialized globals)
#   ZP:   $0002-$00FF (zero page temps/globals)
```

**ROM + RAM hybrid:**
```bash
ln45 -t E000 -d F800 -b 0400 -z 02 -o rom.bin kernel.o45
# Result:
#   ROM CODE: $E000-$FFFF (ROM code in bank)
#   ROM DATA: $F800-$FFFF (constants in ROM)
#   RAM BSS:  $0400-$07FF (runtime BSS in RAM)
#   ZP:       $0002-$00FF (zero page)
```

**Extended memory (MEGA65):**
```bash
ln45 -t 2000 -d 8000 -b 9000 -o program.prg main.o45
# Result:
#   CODE: $2000-$7FFF (main RAM, 24KB)
#   DATA: $8000-$8FFF (bank 1, 4KB)
#   BSS:  $9000-$9FFF (bank 1, 4KB)
```

## Library vs Direct Linking

### Direct Linking (Flat object files)

Link all modules directly without archiving:

```bash
# Compile multiple modules
cc45 -c main.c -o main.o45
cc45 -c util.c -o util.o45
cc45 -c math.c -o math.o45

# Link all directly
ln45 -prg -o program.prg main.o45 util.o45 math.o45
```

**Pros:**
- Simple, straightforward
- Useful for single-purpose programs
- All symbols must resolve

**Cons:**
- All objects always included (bloats executable)
- No selective linking — can't include only used functions
- Large link time with many objects

### Library Linking (`.lib` archives)

Archive modules into a library, linker pulls only what's used:

```bash
# Create archive
ar45 -r mylib.lib util.o45 math.o45

# Link with selective inclusion
ln45 -prg -o program.prg main.o45 -l mylib.lib
```

**Pros:**
- Only used functions included (smaller binaries)
- Easy to reuse across projects
- Standard C library workflow (`c45.lib`, `c45_zp.lib`)
- Symbol lookup: linker scans archive members as needed

**Cons:**
- Requires archiving step
- Library member organization matters (related functions per object)

### Real-world comparison

**Scenario:** Build a game with shared sprite, sound, and physics libraries.

**Direct approach** (don't do this):
```bash
# All objects compiled separately
cc45 -c game_main.c -o game_main.o45
cc45 -c sprite_*.c -o sprite_*.o45      # 20 objects
cc45 -c sound_*.c -o sound_*.o45        # 15 objects
cc45 -c physics_*.c -o physics_*.o45    # 10 objects

# Link all 46 objects
ln45 -prg -o game.prg game_main.o45 sprite_*.o45 sound_*.o45 physics_*.o45
# Result: 150KB executable with every sprite/sound/physics function
```

**Library approach** (recommended):
```bash
# Archive libraries
ar45 -r sprite.lib sprite_*.o45
ar45 -r sound.lib sound_*.o45
ar45 -r physics.lib physics_*.o45

# Link with selective inclusion
ln45 -prg -o game.prg game_main.o45 -l sprite.lib -l sound.lib -l physics.lib
# Result: 60KB executable with only used sprite/sound/physics functions
# game_main calls sprite_draw → only sprite_draw.o45 pulled from archive
```

### Mixed linking

Combine direct and library linking:

```bash
# Critical functions compiled directly, optional in libraries
ln45 -prg -o program.prg \
  main.o45 startup.o45 \
  -l stdlib.lib -l mylib.lib -l c45.lib
```

Each direct `.o45` is fully included; each library member is conditionally included.

## Thunk Generation in Detail

When linking objects compiled with different calling conventions, the linker automatically generates bridge code (thunks) to translate between them.

### When Thunks Are Needed

| Caller Conv | Callee Conv | Needed? | Thunk Type |
|-------------|-------------|---------|-----------|
| Stack | Stack | No | — |
| Stack | ZP | Maybe | `__thunk_s2z_*` |
| ZP | Stack | **Yes** | `__thunk_z2s_*` |
| ZP | ZP | No | — |
| SAC | Any | No | (SAC uses stack convention) |

**Rule:** ZP callers need thunks for stack callees. Stack callers can call ZP callees directly (parameters converted by thunk).

### Stack → ZP Thunk

When a stack-calling function calls a ZP function:

```c
// main.c (compiled with default stack calling convention)
extern int add_zp(int a, int b);  // ZP function from zp_lib
int main(void) {
  return add_zp(3, 5);             // Stack convention call
}

// zp_lib.c (compiled with -fzpcall)
int add_zp(int a, int b) {
  return a + b;
}
```

**Generated thunk** (`__thunk_s2z_add_zp`):
```asm
; Stack → ZP thunk for add_zp
; On entry: parameters on stack (pushed in reverse order)
; Stack: [RET_HI | RET_LO | ARG2_HI | ARG2_LO | ARG1_HI | ARG1_LO | ...]
__thunk_s2z_add_zp:
  pla                   ; Retrieve ARG1_LO from stack
  sta $20               ; Store in ZP param slot for ARG1
  pla                   ; Retrieve ARG1_HI
  sta $21
  pla                   ; Retrieve ARG2_LO
  sta $22
  pla                   ; Retrieve ARG2_HI
  sta $23
  jmp add_zp            ; Jump to actual ZP function
```

Thunk is transparent to caller — normal stack call, normal ZP implementation.

### ZP → Stack Thunk

When a ZP-calling function needs to call a stack function:

```c
// zp_app.c (compiled with -fzpcall)
extern int strlen_stack(const char *s);  // Stack function from c45.lib
int my_strlen(const char *s) {
  return strlen_stack(s);  // ZP convention call
}
```

**Generated thunk** (`__thunk_z2s_strlen_stack`):
```asm
; ZP → Stack thunk for strlen_stack
; On entry: parameter in ZP param slot ($20, $21)
__thunk_z2s_strlen_stack:
  lda $21               ; Load ARG1_HI (ZP param)
  pha                   ; Push for stack convention
  lda $20               ; Load ARG1_LO
  pha
  jsr strlen_stack      ; Call stack function
  ; Return value in A/X, already correct for ZP caller
  rts
```

### Thunk Performance

- **Stack→ZP**: ~40-50 cycles (load params, store ZP, jump)
- **ZP→Stack**: ~30-40 cycles (load ZP, push stack, call, return)
- **Direct call**: ~4 cycles (JSR overhead)

**Thunk overhead**: ~10-40× slower than direct call. For hot paths, prefer consistent calling convention at compile time.

### Controlling Thunk Generation

```bash
# Default: warn on mismatches, generate thunks
ln45 -prg -o program.prg main.o45 -l c45.lib

# Error on mismatches (no thunks)
ln45 --no-thunks -prg -o program.prg main.o45 -l c45.lib
# Error: 'add_zp' uses ZP calling convention, caller uses stack

# Suppress warnings (still generate thunks)
ln45 -prg -o program.prg main.o45 -l c45.lib 2>/dev/null
```

## Error Messages

| Error | Cause |
|-------|-------|
| `undefined symbol '_foo'` | An object imports `_foo` but no object exports it |
| `duplicate symbol '_foo'` | Two objects both export `_foo` |
| `relocation offset out of range` | A relocation entry points past the end of a segment |
| `invalid symbol index` | A relocation references a non-existent import table entry |

## Output Format

Without `-prg`: raw flat binary (text + data, gap-filled if needed).

With `-prg`: 2-byte little-endian load address header followed by the binary. The load address is the text base (`-t` value). This format is directly loadable on the MEGA65/C64.

BSS is not included in the output — it must be zeroed at runtime (by `crt0` or the startup code).

## Function Metadata (ZP Calling Convention)

When object files are compiled with `-fzpcall` or contain `__fastcall__` functions, each function may include metadata directives that describe its zero-page and register usage. These are stored as 17-byte function attribute records in the `.o45` symbol table.

| Directive | Purpose |
|-----------|---------|
| `.zp_uses $03, $04, ...` | ZP slots read as input parameters |
| `.zp_clobbers $03, $04, ...` | ZP slots this function may overwrite |
| `.zp_release $07, $08, ...` | ZP slots consumed (caller need not restore) |
| `.reg_clobbers A, X, Y` | CPU registers not preserved across the call |
| `.flag_clobbers C, N, Z` | Processor flags not preserved |

The linker reads this metadata to build call graphs and compute transitive clobber sets for interprocedural optimization. Objects without function attributes are treated conservatively as "clobbers all, releases none".

## Diagnostics

The linker emits warnings to stderr for potential issues:

| Warning | Meaning |
|---------|---------|
| `warning: symbols 'X' and 'Y' overlap at $NNNN (different segments)` | Two symbols from different segment types (e.g., TEXT and DATA) were placed at the same address. This usually indicates a bug in the assembler's segment assignment. |
| `ln45: warning: unused global symbol 'X' (defined in FILE.o45)` | A symbol was marked as `.global` (exported) but is not referenced by any other module in the program. Internal symbols (names starting with `__`) are suppressed. This helps identify dead code. |

## Map File Format Reference

Use `-M <file>` to generate a detailed linker map. The map file is human-readable and useful for memory analysis, symbol lookup, and debugging.

### Map File Structure

```
Linker Map
==========

Memory Layout
-------------
  <SEGMENT>  $<START> - $<END>  (<SIZE> bytes)
  ...

Object Files
------------
  <FILE>
    <SEGMENT>  $<START> - $<END>  (<SIZE> bytes)
    ...
  ...

Symbols (by address)
--------------------
  $<ADDR>  <NAME>                          <FILE> [<FLAGS>]
  ...
```

### Memory Layout Section

Summarizes total memory usage for each segment:

```
Memory Layout
-------------
  TEXT   $2000 - $203B  (60 bytes)
  DATA   $203C - $2041  (6 bytes)
  BSS    $4000 - $4FFF  (4096 bytes)
  ZP     $0002 - $007F  (126 bytes)
```

**Interpretation:**
- `TEXT`: Code section (loaded into binary)
- `DATA`: Initialized globals (loaded into binary)
- `BSS`: Uninitialized globals (zeroed at runtime, not in binary)
- `ZP`: Zero page globals (fast 8-bit addressing)

### Object Files Section

Shows how each input object contributed to each segment:

```
Object Files
------------
  main.o45
    TEXT  $2000 - $2007  (8 bytes)
    DATA  $203C - $2041  (6 bytes)
  crt0.o45
    TEXT  $2008 - $200E  (7 bytes)
  utils.o45
    TEXT  $200F - $203B  (45 bytes)
    BSS   $4000 - $400F  (16 bytes)
    ZP    $0002 - $001F  (30 bytes)
```

**Reading:**
- Each object occupies a contiguous block within each segment
- Objects are linked in input order
- BSS and ZP are summed (not concatenated in binary)
- Missing segments indicate no contribution to that segment

### Symbols Section

Lists all exported symbols with their final addresses:

```
Symbols (by address)
--------------------
  $2000  _main                          main.o45
  $2008  __init                         crt0.o45
  $200E  _init_features                 crt0.o45 [weak]
  $200F  _puts                          utils.o45
  $203C  _result_buf                    main.o45 [DATA]
  $4000  _heap_start                    utils.o45 [BSS]
  $0002  _zp_counter                    main.o45 [ZP]
```

**Flags:**
- `[weak]` — Weak symbol (can be overridden by a strong symbol)
- `[DATA]` — Symbol is in DATA segment
- `[BSS]` — Symbol is in BSS segment
- `[ZP]` — Symbol is in zero page

No flags → symbol is in TEXT segment.

### Using the Map File

**Find symbol address:**
```bash
grep "_main" program.map
# Output: $2000  _main                          main.o45
```

**Analyze memory usage:**
```bash
# Check how much code vs data
head -20 program.map

# Find largest symbol (requires custom script)
```

**Verify layout:**
```bash
# Check segment boundaries don't overlap
# TEXT should end before DATA starts
# DATA should end before BSS/other segments
grep "Memory Layout" -A 5 program.map
```

**Debug relocation issues:**
```bash
# Use `-M` output to verify symbols are placed correctly
# Check for unexpected overlaps or gaps
grep "overlap" program.map
```

## Limitations

- **Custom segments**: The `.o45` format supports four segment types: TEXT, DATA, BSS, and ZP. User-defined segments (`.segment "myname"`) are mapped to TEXT in `.o45` output. Custom segments work correctly in flat binary mode (`ca45` without `-c`) but lose their identity in relocatable objects. Use the standard segment directives (`.code`, `.data`, `.bss`, `.zp`) for relocatable builds.
