# ln45 — Linker for .o45 Object Files

`ln45` links `.o45` relocatable object files and `.lib` archives into a flat binary or a PRG executable. It pulls the library members it needs, lays out and merges the segments, resolves symbols, bridges calling-convention mismatches with thunks, checks static-allocation (SAC) safety, and applies relocations.

`cc45 file.c` (without `-c`/`-S`) runs `ln45` for you: `ln45 -basic -o <out> <obj> <extra libs> <c45.lib | c45_stack.lib>` (or `-prg -t <base>` with `cc45 --prg-base`).

## Usage

```bash
ln45 [options] <file1.o45> [file2.o45 ...] [-l lib.lib ...]
```

Any argument ending in `.lib` is taken as a library (same as `-l`); every other non-option argument is an object file. Options and files may be mixed in any order. `ln45` reads no configuration file.

## Options

| Flag | Description |
|------|-------------|
| `-o <file>` | Output filename (default: `a.out`, or `a.prg` for a PRG) |
| `-prg` | Write a PRG: 2-byte load address (the text base) + image. Also selected when the `-o` name ends in `.prg` |

## Linking Process

### 1. Library resolution
Undefined imports of the input objects are looked up in the symbol index of each library, in command-line order. The defining member is added to the link; its own imports are added to the undefined set, and the scan repeats until nothing new is pulled. A symbol already defined by an object (even weakly) does not pull a member. Pulled members are named `lib(member.o45)` in diagnostics and the map.

A pulled member's import bound to the program's own definition of a name a library member also defines (not weakly: weak library definitions such as `_init_features` are meant to be replaced) warns, once a name (#346): `ln45: warning: '_putchar' of main.o45 overrides the library's (c45.lib(asm_putchar.o45)), which c45.lib(zp_vprintf.o45) uses`. Deliberate replacements link as before; `-Wno-override` silences it.

Then ln45 drops what nothing live reaches. The units are the sections of a sectioned object (`OPT_SECTIONS`, written by `cc45`/`ca45 -ffunction-sections`: a function, a `.split` piece) and each object's residual (the bytes no section covers, kept whenever anything of the object is); an unsectioned object is a single unit. The roots are the input objects (kept whole; with `--gc-inputs` only through what reaches them), the startup code (an `init` sub-segment), `.keep` sections and `-u` symbols. A live unit's relocations make their targets live: an import through the definition the link uses (the first strong one, else the first weak one; `X__ar` / `X__ar_N` reach `X`; a strong definition counts only in an object found live, #358: the walk starts with the roots' strong definitions and is repeated, adding those of the objects it found live, until no more become live, so a member pulled in only by a reference from code that is then dropped does not replace a weak default), an internal relocation through its section reference (`OPT_SECTREF`) or the section its stored value lies in, and a `.ref` (an import the section needs without a relocation) through that import's definition.

Members with nothing live are dropped (a member whose weak definitions all lost — the integer `printf` once the float one is linked — and one only such a member needed, `sprintf`). A sectioned member with dead sections is rewritten without them before layout: its bodies shrink (a kept section keeps its offset modulo its alignment), relocation sites, exports, line info and imports used only by dropped code go or move, and internal relocations' stored values follow their targets. A live relocation into a dropped section is an error (`dropping unused sections: ...`). A program using `gotoxy` from a sectioned `conio` keeps 4 of its 23 functions (11294 → 967 bytes). Objects with more than one text sub-segment are kept whole.

The map lists "Discarded Library Members" and "Discarded Sections"; `--print-gc` (or `-v`) prints them (`ln45: dropped section lib.lib(conio.o45): _cprintf (1039 bytes)`); `--no-gc` keeps everything pulled.

The startup code is a library member (`crt0_zp.o45` in `c45.lib`, `crt0.o45` in `c45_stack.lib`), pulled in by the references every cc45 object makes to it (`__bp_rom`/`__bp_prog`), so a C program links with just its objects and the standard library. Its `init` sub-segment is placed first, at the text base.

### 2. Layout
- **Text**: object text bodies are grouped by sub-segment (`OPT_SEGATTR` records, see [lib45](../architecture/lib45.md#16-sub-segment-attributes-opt_segattr)): all `init` chunks first (crt0 startup), then `code`, then other names in alphabetical order. Objects without sub-segment records are one `code` chunk. Within a group, objects keep command-line order (pulled library members follow the input objects).
- **Data / BSS / ZP**: concatenated in object order. The objects' ZP segments (ca45 `.segment "zp"`) go into the program's base page, below the `__zp` variables (`__zp_page` + their place: a base-page operand's `R_LOWX` gets the place, an `R_WORD` the full address), when the program has one (crt0's `__zp_page`) and `-z` gives no address; otherwise at `-z` or `$02`.
- **Alignment**: an object exporting `cc45.align.text`, `cc45.align.data` or `cc45.align.bss` (emitted by cc45 for `_Alignas`/`aligned(N)`) is placed so its aligned items land on that boundary; the data and BSS bases are rounded up to the largest such alignment.
- Data starts after text and BSS after whichever of text and data ends last, unless `-d`/`-b` are given. The image covers text and data at their addresses with zeros in between (`test_ln45_layout_xemu.c`).

### 3. Symbol resolution
- Exports are collected into a global map: `segment base + object offset + symbol offset` (absolute exports keep their value).
- A strong definition overrides a weak one; two strong definitions are an error; of two weak ones the first wins. With dead-code removal (the default), a strong definition in a library member overrides only when the member is reached from live code (#358; see above): a member pulled in only by code that is dropped is dropped with its strong definitions.
- Every import must resolve (an import `X__ar_N` resolves through `X__ar` plus offset `N`).
- Linker-defined symbols (unless an object defines them):

| Symbol | Value |
|--------|-------|
| `__bss_start` | BSS base |
| `__bss_end` | End of BSS, including the base page(s) below |
| `__bss_fill` | The byte crt0 fills BSS with: `--bss-fill=V`, default `0` |
| `__stack_size` | The CPU stack's share below `__stack_top`, where `malloc`'s automatic heap ends: `--stack-size=N`, default `4096` |
| `__zp_page` | Only if some object imports it (crt0 does): a page-aligned 256-byte block after BSS, used as the program's relocated base page |
| `__zp_page_isr` | With `__zp_page`: the page after it when any object has an `__interrupt` function (`FUNC_FLAG_ISR`), else equal to `__zp_page` |

`__stack_top` is not linker-defined: `c45.lib`/`c45_stack.lib` provide `$BFFF` (`asm___stack_top.o45`); cc45 defines it in the main object for `-fstack-top=` and as `0` for `-fno-stack16`.

### 4. Function metadata checks
From function attribute records and JSR relocations ln45 builds a call graph, computes transitive clobber sets (shown in the map), and then:
- **Calling conventions** — see [Thunks](#calling-convention-thunks).
- **SAC safety** — a function using static allocation (`FUNC_FLAG_STATIC_ALLOC`) that can reach itself through the call graph (recursion across modules), or that is reachable from an `__interrupt` handler, is a link error. Mark such functions `#pragma cc45 recurse`.

### SAC overlay

A SAC function keeps its parameters and locals in a BSS block (`<f>__ar`, size `cc45.sacsize.<f>`, emitted by cc45 with pad bytes around it so that a pointer just past a variable never names a different piece of BSS). Two SAC functions whose blocks can share memory are ones where neither reaches the other through calls, so they are never active at the same time. ln45 moves these blocks into one overlay area at the end of BSS (before `__zp_page`). It places them first fit, largest first, and a block never overlaps the block of a function it conflicts with.

- **Calls** are `JSR` and `JMP` relocations to a function. In objects not made by cc45 (assembly, crt0), an exported label also "calls" the next one (its code can fall through).
- **Address-taken functions**: a function referenced in any other way (an address loaded with `#<`/`#>`, stored in data) can be called through a pointer, by the functions that call through pointers. cc45 marks those, and `cc45.icallinfo` on an object says it marks them; every label of an object without it counts as calling through any pointer.
  - `cc45.icall.<f>`: `f` calls through a pointer of unknown type (an unprototyped one, `int (*)()`, a cast at the call, a virtual call) or has inline asm. ln45 adds a call from it to every address-taken function.
  - `cc45.isig.<f>.<sig>`: `f` calls through a prototyped pointer whose parameters take the slots `<sig>` (`s2_4`: a 2-byte and a 4-byte one, `char` and pointers 2, `long` 4, `float` 5, a struct by value 2; `v` after a variadic list; the return type does not count). ln45 adds a call from it to each address-taken function with the same `cc45.fsig.<g>.<sig>` (every cc45 function says its own) or `cc45.fsig.<g>.any`, and to each address-taken label that says none unless its object has `cc45.icallinfo`: a marked asm object vouches that its labels are not called through pointers, except those it gives `cc45.fsig.<g>.any` (the library's `exit` and `__builtin_*` aliases, which call C code).
  - A pointer whose type does not match the function it points to (a function cast to another pointer type and called through it) is undefined behaviour in C, and here the two functions may then share storage.
  
  Such a function shares storage only with functions never active while it can run. `ln45 -vv` lists each function's indirect calls and the address-taken functions (`call graph: ...`).
- **Functions in code overlays** take part like resident ones: their blocks are resident BSS, which swapping overlays never touches, and a call into an overlay (through its stub and `__ovl_call`) is a call in the graph. So a function in overlay A and one in overlay B share storage unless one can reach the other, for instance A → resident code → B (`src/test-resources/sacovl/`). vim2, 27 overlays: 12,742 → 7,622 bytes of BSS.
- **Blocks that stay in place**: blocks in an object with aligned BSS (`cc45.align.bss`) or with a plain `R_LOW` relocation into BSS (only the low byte of the target is known; ca45 writes `R_LOWX`), blocks without a size marker, and the blocks of weak definitions the link does not use.
- **When nothing is shared**, the layout is left unchanged.

`--no-sac-overlay` turns the overlay off (every block stays where its object put it). `-v` prints `SAC overlay: N functions, X bytes of storage in Y (Z saved)`, and the map's segment summary shows the overlay area. Because of the overlay, a SAC function's locals never keep their values between calls (as in standard C for automatic variables).

### Base-page blocks

A static-allocation function compiled by cc45 that makes calls keeps its most used variables in a base-page block of its own (`.zar $80, N`, size `cc45.zarsize.<f>`; its base-page operands are relocated against `<f>__zar`). ln45 places the blocks in the program's base page (`__zp_page`) from the end of the register pool (`$30`–`$7F`) the program uses up to `$F1`: every object says how far into the pool its instructions reach (ca45's `cc45.bptop`; an object without it counts as using all of it), and the area starts at the largest (`ln45 -v` prints `base-page area: $46-$F1`). Callers are placed before callees, each at the lowest bytes no function active together with it uses (the area needed is then about the heaviest call path): like the SAC overlay, two functions share bytes when neither reaches the other through calls. Calls through pointers are edges too: a function that makes them (cc45 marks it with `cc45.icall.<f>`; every label of an object not made by cc45 counts as one) can call every function whose address is used. `<f>__zar` is `__zp_page` + the block's base-page address. When the functions active together need more than the area, a block that does not fit goes where it shares the fewest bytes with blocks of functions active together with it, and ln45 warns (`base-page storage: ...`). The function on the inside of each such pair (the callee; both when a function whose address is used is involved) is then reached through a generated wrapper: it saves the block's bytes, takes the caller's return address off the stack (so stack-convention arguments stay where the function expects them), calls the function, keeps A/X/Y/Z, and restores the bytes and the return address. Every reference to the function — calls, `__sac` entries, convention thunks, its address in code or data (function pointers) — goes to the wrapper. The program is correct; those calls cost about 10 cycles per byte of the block. Compiling the modules with `cc45 -fno-zp-locals` avoids it. `-v` prints `base-page blocks: N functions, X bytes in Y`, and the map's segment summary shows the area used.

#### The program-wide base-page plan

cc45 picks a function's block variables one file at a time (pointers first, then by use, 16 bytes at most): it cannot see which functions are active together, so the blocks of deep call chains overflow into wrappers while bytes elsewhere stay unused. A two-pass build lets ln45 choose for the whole program (#304):

```bash
cc45 -O2 -c a.c -o a.o45; cc45 -O2 -c b.c -o b.o45
ln45 -basic --zp-plan-out=prog.zar -o prog.prg a.o45 b.o45 c45.lib      # pass 1: writes the plan
cc45 -O2 -fzp-plan=prog.zar -c a.c -o a.o45; cc45 -O2 -fzp-plan=prog.zar -c b.c -o b.o45
ln45 -basic -o prog.prg a.o45 b.o45 c45.lib                             # pass 2
```

- **The candidates.** cc45 records every candidate of every static-allocation function that makes calls, whatever its options (`-fno-zp-locals` too): `cc45.zc.<storage symbol>` = its size, whether a pointer, its uses and its loads/stores through it.
- **The choice.** Each candidate is worth its uses times its size (an absolute access takes a byte more per byte) plus, for a pointer, 10 bytes per load or store through it (the copy to `__zp_scratch` a base-page pointer saves). Greedy by value per byte, a variable joins its function's block when every block still fits where ln45 places them (callers before callees, first fit): no wrapper. Library functions keep their blocks (they are not recompiled); a function's block is at most `$80`–`$F1` (114 bytes).
- **The file.** A comment with the bytes chosen and their estimated value, then `fn <function> <storage symbol>…` for every planned function. `ln45 -v` prints `base-page plan: N functions, X bytes chosen`.
- **Pass 2.** A function the plan lists takes exactly those variables (no cap, `-fno-zp-locals` ignored); a file's `__zp` variables then go at the top of `$80`–`$F1` and its planned blocks stop below them. ln45 places the blocks as always: with every file built with the plan nothing is wrapped. A plan that no longer matches the code (edited sources, other options, a file built without it) leaves blocks that do not fit to the save/restore wrappers, as without a plan: correct, but larger and slower, so rebuild with a fresh plan. A plan written from pass 2 is the same, so two passes converge.
- **vim2:** pass 1 (its own options, ten files with `-fno-zp-locals`) is today's build; pass 2 is 6,716 bytes of code smaller (154,402 instead of 161,118; overlays 139,721 instead of 146,480), with no wrapper. Test: `src/test-resources/zp_plan/` in `test_xemu.sh` (both conventions, a 22-byte block, the plans of both passes equal, a stale plan).

### `__zp` variables

cc45 `__zp` globals (`cc45.zpvar.<sym>` = size, from the file that defines it; their operands are relocated against `<sym>`, ca45 `.zpsym`) are placed at the top of `$80`–`$F1` of the program's base page, in name order, then the objects' ZP segments below them, before the base-page blocks, which share the rest. `<sym>` is `__zp_page` + its address. More than the area holds, or a variable defined in two objects, is an error. A variable with an initial value (`cc45.zpinit.<sym>`, in data) is copied into the base page by a generated `__zp_init` (a copy loop per variable, appended to the text), which crt0 calls after the BSS fill instead of its weak `rts`. A base-page operand of a `__zp` variable or of a ZP segment (`R_LOWX`) in a function an `__interrupt` handler reaches is an error: the handler runs on its own base page. `-v` prints `__zp variables: N, X bytes`, and the map's segment summary shows the area.

### `__section` variables

cc45 `__section("NAME")` variables have no storage in their objects: ln45 defines their symbols. Each object records its part of a section, `cc45.sectsize.NAME` (weak, its bytes), the section's address when the file declared one, `cc45.section.NAME` (weak; all objects must agree, `--section NAME=ADDR` overrides them, and a section without one is an error), and each variable's offset in its part, `cc45.sectvar.NAME.<sym>` (a `static` variable's symbol is `<name>__<file>`). The parts follow each other from the section's address in link order; a variable defined in two objects, a section past `$FFFF`, two sections that overlap are errors, and once the program is laid out so is a section over the program (text to the end of BSS and its base page), the CPU stack's share or the code overlays' region; one in malloc's heap (`__heap_ptr` linked) is a warning. A variable with an initial value (`cc45.sectinit.<sym>`, in data) is copied there at startup by `__zp_init`: a DMA copy job each (12 bytes after its `rts`; list bank, high byte, low byte to `$D702`/`$D701`/`$D700`, as crt0's BSS fill). Dead-section removal keeps every `cc45.sectinit` part (the data may be for the hardware, never named in C) and takes an import of `<sym>` to the object that records it. A `__section` function's code is the text sub-segment `sect.NAME`: its objects' chunks, in link order, are linked to run at the start of the section (its variables follow them), and a copy of the relocated code, reserved in the program's text after the other chunks, is copied there by a `__zp_init` DMA job too. `-v` prints `section NAME: N bytes at $ADDR`; the map's segment summary has a `SECT` line per section (with its bytes of code).

### 5. Thunks, relocation, output
Thunks are appended to the text segment (data/BSS move up if they were placed automatically), relocations are applied, and the image is written: text, then data (a gap between text end and a higher `-d` address is zero-filled). BSS is never written; crt0 zeroes it.

### 6. Stack room check
For a C program (one with crt0's `__zp_page`), ln45 fails when the program end (`__bss_end`, or the end of `__zp_page` / `__zp_page_isr`) is above `$C000` (`--ram-top`), with either stack, and when `__stack_top` is `$C000` or above (`-fstack-top=$FFF0` would put the stack in ROM and I/O). If `__stack_top` is non-zero, ln45 also fails when the program end is above it, and warns when fewer than 512 bytes are left for the 16-bit CPU stack. When the program uses `malloc` with the automatic heap bounds (`__heap_start`/`__heap_end` 0), it warns when the program reaches the heap's end (`__stack_top + 1 - __stack_size`, or `$C000` with the 8-bit stack) — `ln45: warning: no heap: the program ends at $B400, at or above the heap's end $B000 ...; malloc returns NULL` — or leaves it less than 1 KB.

## Relocation Types

| Type | Patch | Description |
|------|-------|-------------|
| `R_WORD` | 2 bytes | 16-bit address |
| `R_LOW` | 1 byte | Low byte of an address (older objects; a BSS target makes the object's SAC blocks stay in place) |
| `R_LOWX` | 1 byte | Low byte of an address (the record carries the high byte for the addend); what ca45 writes |
| `R_HIGH` | 1 byte | High byte of an address (the record carries the low byte for the addend) |
| `R_LINEAR24` | 3 bytes | 24-bit linear address |
| `R_LINEAR32` | 4 bytes | 32-bit linear address |
| `R_SEGADR` | 3 bytes | 24-bit address (written like `R_LINEAR24`) |
| `R_IMM8` / `R_IMM16` | 1 / 2 bytes | Immediate operands (self-modifying-code parameters) |

For an external reference the bytes already at the patch site are the addend (`sym+4`); for an internal one they hold the assembly-time address, from which the object's segment base is subtracted before adding the final segment address.

## Output Format

- **Flat binary** (default): text + data, no header.
- **`-prg`**: 2-byte little-endian load address (the text base), then the image.
- **`-basic`**: load address `$2001`, then a 12-byte BASIC program `10 SYS 8205` (next-line link, line number 10, `$9E` SYS token, the decimal address, `$00`, end-of-program `$00 $00`), then the image at `$200D`. With `-t <addr>` the stub is `10 SYS <addr>` (13 bytes for a 5-digit address) and zero bytes fill the file from the end of the stub up to `<addr>`.

## Examples

All examples were run with the current toolchain (`c45.lib` from `lib/build`, put on `CC45_LIB` or given with a path).

### Separate compilation

```bash

### Libraries

```bash

ln45 -basic -o program.prg main.o45 mylib.lib -l c45.lib     # or -l mylib.lib
ln45 -basic -o program.prg main.o45 -L ./libs -l mylib.lib -l c45.lib

Put your own libraries before `c45.lib` only for readability — resolution repeats over all libraries until nothing changes, so order does not matter for dependencies; it matters only when two libraries define the same symbol (the first one listed is searched first).

## Code Overlays

A program can be larger than bank 0: an object exporting `cc45.overlay.<name>` (cc45 `#pragma cc45 overlay(name)` or `-foverlay=name`, ca45 `.overlay name`) has its code in the code overlay `<name>`. Several objects (C or asm) can name the same overlay: they share it, each defining the marker (#328).

- **Layout.** Every overlay is linked to run at one region (`__ovl_region`, page-aligned, as large as the largest overlay) right below the stack's share (`__stack_size` below `__stack_top`; `$C000` with the 8-bit stack); `__heap_end` becomes the region's start, so `malloc`'s heap ends there. An overlay's data and BSS stay with the program's: they keep their values while other overlays run. The program must end (BSS and its base page included) below the region, and the largest overlay must fit below the stack: both are link errors otherwise.
- **The overlay file.** The overlays' code goes to its own file (`--overlay-out`, default `<output>.ov1`): a 2-byte load address, then the images one after another (mapped ones each on a 256-byte boundary). Their description, for [nm45](nm45.md#code-overlay-files) and [objdump45](objdump45.md), goes next to it in `<output>.ovd`, which the program never loads (`"OVL45"`, version 2, the region, flags and count; per overlay its code file (1: `.ov1`), offset in it, far address, length and name; per symbol its overlay, run address and name; the description's length (4 bytes) and `"OVL45"` at the end; `include/O45OverlayFile.hpp`). Copy the `.ov1` to the program's disk under the name the program loads it by (`--overlay-name`, default `<OUTPUT>.OV1`; ln45 prints it). Its runtime's `__ovl_init`, called by crt0 before `main`, loads it into far memory (`--overlay-store`, default `$50000`) through the KERNAL (`SETBNK` with the data bank in A and the name's bank in X, `SETNAM`, `SETLFS` with secondary address 1, `LOAD` to the address the file starts with) from the drive the program was loaded from (8 when none is known); a missing file prints `?OVERLAY FILE` and aborts (exit status `$FFFE`). Each overlay goes into the first range of `--overlay-store` with room for it (never across a bank); the ranges are taken a 64 KB bank at a time, and each bank that holds overlays is a file of its own, numbered in the ranges' order: `<output>.ov2`, … (on the disk the name's last character counted up: `<OUTPUT>.OV2`; with several files `--overlay-name` and `--overlay-out` must end in a digit, so 9 files at most), which `__ovl_init` loads into its bank (`__ovl_file`: the number of files, the name, then a record of 8 bytes per file: the name's last character, the bank it is loaded into, the attic RAM megabyte and bank it is copied to (0: none), its address and length). The `.ovd` gives each overlay's file. An overlay that fits in no range is a link error, which names a range to add. ln45 defines where the files lie (C: `__ovl_store_bank`, `__ovl_store_first`, `__ovl_store_last`, and `__ovl_store2_bank`, `_first`, `_last`, for the files in banks 4 and 5, else 0; the bank and the first and last offset in it): `far_malloc` (`<far_ptr.h>`, banks 4-5) never hands out those parts of its banks. Test: `src/test-resources/overlay/` in two banks (`test_xemu.sh`).
- **Calls.** A `JSR`/`JMP` from an overlay to a function of the same overlay is direct. Every other reference to an overlay's function — a call from resident code or another overlay, its address taken (in code or in data: function pointers, tables), a thunk or base-page wrapper — goes to a resident stub of 6 bytes (#332), `jsr __ovl_calli` followed by the overlay's id and the function's address: `__ovl_calli` reads them after its return address, pulls it off (the caller's own return address is then on top, as before) and goes on in `__ovl_call` (`lib/stdlib_asm/ovl.s45`, which ln45 links when a program has overlays). With `--overlay-fast-stubs` a stub is 21 bytes (`sta __ovl_sa`, the id and the function stored by immediate loads, `jmp __ovl_call`), a few cycles faster per call; vim2's 159 stubs take 2,341 bytes less of bank 0 in the small form. `__ovl_call` moves the caller's return address, and the overlay to bring back on the return, to a 32-entry overlay return stack. That overlay is the one the innermost overlay call still running entered: the caller's own for a call from the region, and also for a call from resident code that an overlay called (overlay a → resident → overlay b: a comes back when the resident function returns into it); none at the top level. It copies the overlay into the region by DMA when another one is there (about 0.1 ms per KB), and jumps to the function with the stack as the caller left it (both calling conventions find their arguments where they expect them). The return copies that overlay back if another was copied in meanwhile (a resident function called from the top level, `main` → `a`, then `main` → `b`, causes no copying back). A, X, Y, Z go in unchanged and the result and the flags come back unchanged.
- **Limits.** An `__interrupt` handler in an overlay (or `__far`) is a link error (interrupts must find their code), and so is an overlay function an interrupt handler reaches through its calls: the runtime (`__ovl_call`, its stub variables and return stack) is not reentrant. ln45 follows direct calls and calls through pointers (a function that makes them reaches every function whose address is used, as for the SAC overlay) and names the chain: `'_tick' (code overlay far1) is reachable from interrupt handler '_handler' (_handler -> _helper -> _tick)`. Calls through overlays nest 32 deep (deeper aborts). A program can have up to 255 overlays (an overlay's id is a byte; the `__far` functions' `far1`, `far2`, … count too); more are a link error (`code overlays: 256 overlays ...; an overlay's id is a byte: at most 255`). The runtime finds each overlay's far address and length (or its MAP registers) in six tables of a byte per overlay that ln45 writes after the stubs (`__ovl_table0`…`__ovl_table5`, indexed by id − 1). `setjmp`/`longjmp` work across overlay calls: `setjmp` also saves the overlay return stack's depth and the overlay in the region (`jmp_buf` bytes 6-7, through `__ovl_jsave`), and `longjmp` drops the calls it leaves and brings that overlay back (`__ovl_jrestore`; crt0 has empty weak versions for programs without overlays). Copied overlays that call each other in a tight loop copy on every call (mapped ones only change the map).
- **From C.** `<overlay.h>` declares `__ovl_current` (the overlay in the region: 1, 2, … in the order ln45 meets the objects, 0 before the first call) and `__ovl_region`.
- **Inspecting.** The map (`-M`) shows where the overlays run and in which bank each is kept, and lists their symbols and source lines per overlay (see [Map File Format](#map-file-format)). [nm45](nm45.md#code-overlay-files) and [objdump45](objdump45.md) read the `.ovd` and `.ov1` files.

```bash
cc45 -O2 -c main.c -o main.o45
cc45 -O2 -c tool.c -o tool.o45          # #pragma cc45 overlay(tool)
ln45 -basic -o prog.prg main.o45 tool.o45 c45.lib    # also writes prog.ov1, prog.ovd
disk45 create prog.d81 && disk45 add prog.d81 prog.prg PROG && disk45 add prog.d81 prog.ov1 PROG.OV1
```

### Overlays in attic RAM

A range of `--overlay-store` in attic RAM (`$8000000`–`$87FFFFF`, the MEGA65's 8 MB of HyperRAM; xemu has it) keeps copied overlays out of chip RAM altogether: `--overlay-store=0x8000000-0x803FFFF` leaves banks 4 and 5 to `far_malloc`, and a chip RAM range first with attic RAM after it (`--overlay-store=0x41800-0x4FFFF,0x8000000-0x803FFFF`) puts there what does not fit.

- **Loading.** The KERNAL's `LOAD` reaches chip RAM only, so `__ovl_init` loads each attic RAM file into the staging bank (`--overlay-staging`, default 5) at its own address in the bank, and copies it up by DMA. Those files are loaded first: chip RAM files may use the staging bank too, after them.
- **Calls** are as for overlays in chip RAM: each overlay's 28-bit far address is in the tables, the megabyte in `__ovl_table3`, and `__ovl_call` copies it into the region by DMA. Attic RAM is slower than chip RAM to copy from.
- **Copied only.** `MAP` reaches the first megabyte: `--overlay-map` (and `__far` functions, which are mapped) with an attic RAM range is a link error (`attic RAM (--overlay-store) holds copied overlays only`).
- **The far heap.** ln45 defines `__ovl_attic_bank`, `__ovl_attic_first`, `__ovl_attic_last_bank` and `__ovl_attic_last` (C; 0 without attic RAM files): the bank (`$800`–`$87F`) and offset of the first attic file's start and of the last one's end. `far_attic_enable` and `far_attic_init` leave that span out (the range they are given is cut to its larger side of it), so a program can give them all of attic RAM.
- **The map** (`-M`) shows each file's staging bank and its address in attic RAM. Test: `src/test-resources/overlay/attic_*.c` (and the overlay test with a chip and an attic RAM file) in `test_xemu.sh`.

### Packed overlay files

With `--pack-overlays` (#345) each overlay file is written packed ([pack45](pack45.md)'s format 1, the stream unpacking to where the file's image is kept): its load address, then the stream. In chip RAM it is loaded in place, as far into its store range as the stream needs, and unpacked there; a file for attic RAM is loaded into the staging bank as before and unpacked from there into attic RAM. Its record in `__ovl_file` says so (`$FF` for the attic megabyte, the load address and the packed length), and `__ovl_init` calls `__ovl_unpacker`: the address of `__ovl_unpack` (`lib/stdlib_asm/ovl_unpack.s45`, which calls the library's `__unpack`, `unpack()` of `<unpack.h>`, so a program's own function named `unpack` does not take the call, #346; linked only then; 0 otherwise). What the loader calls must be resident: a program's own `__unpack` in a code overlay is a link error. A file that is not smaller packed, or does not fit in its range in place, is written as it is. The `.ovd` says the files are packed (flags bit 1): nm45 and objdump45 unpack them. Test: the overlay test packed, copied and mapped, in two files and in attic RAM, and a program with its own `unpack()` in an overlay (`overlay/own_unpack_*.c`) (`test_xemu.sh`).

### Mapped overlays

With `--overlay-map` an overlay is not copied: it runs where it is kept, in far memory, seen through a window that `MAP` points at it. Switching overlays changes the map only (no copying, whatever their size).

- **The window** is whole 8 KB blocks of the map's lower half ending at `$8000`: `$6000`–`$7FFF`, or `$4000`–`$7FFF` when the largest overlay is over 8 KB (16 KB at most). Only that half of the map changes: the upper half keeps what the ROM maps there (in C65 mode the KERNAL at `$E000` comes from bank 3 through `MAP`'s upper half, which has one offset for all its blocks), and blocks 0–1 hold the zero page, the stack page, the screen and the program's start. So the program (code, data, BSS and its base page) must end below the window, and the heap moves above it: `__heap_start` becomes `$8000` (it ends at the stack's share as before).
- **Kept** 256-byte aligned in far memory (`MAP` offsets are whole pages), from `--overlay-store`; the file has zeros between the images.
- **The ROM.** At start the runtime takes the map the KERNAL records as current (`$011C`–`$011F`) and keeps its upper half in every overlay's map. It writes each overlay's map there too, so the KERNAL's own map changes — its far calls, the disk code, interrupts — restore the overlay when they restore "the current map"; after every ROM call crt0's `__bp_prog` maps the overlay again all the same (`__ovl_rom_leave`), and `__exit` puts the ROM's map back (`__ovl_exit`). Tested with disk I/O (`fopen`, `fputs`, `fgets`) from inside an overlay.

### `__far` functions

cc45 puts the code of `__far` functions in the text sub-segment `far`
(ca45 `.segment "far"`). ln45 takes each object's `far` chunk out of the
resident text and packs the chunks into **automatic overlays** `far1`,
`far2`, … of 8 KB, or 16 KB when one object's chunk is larger (an
object's chunk over 16 KB is an error). The packing follows the calls, so
that far code calling far code of another object shares its overlay when
both fit (such calls are then direct, with no change of the map):
1. **Weights.** Each `JSR`/`JMP` in one chunk to a far function of
   another chunk counts 4; any other reference (an address taken) counts 1.
2. **Clusters.** From the heaviest pair of chunks down, two clusters are
   merged when they fit in one window together.
3. **Overlays.** The clusters go in largest first. Each goes into the
   overlay it has the most calls with among those with room; with no
   calls, into the first with room; with no room anywhere, into a new
   overlay.

A chunk is never split: ca45 may use relative `BSR`s inside it. Put far
functions that call each other in the same file, or in files that fit in
one window together. The weights count call sites, not how often they
run, so a call in a loop counts the same as one made once. They
are mapped overlays: an object with `far` code turns `--overlay-map` on,
for its `.overlay` overlays too. Everything else is as for any overlay:
the overlay file, the stubs, `__ovl_call`. The objects' other text stays
resident, and a call from an overlay to code of another chunk of the same
object goes through the stub as well. A function's attribute record, its
line info and its static storage go with it. The map lists the automatic
overlays like the others.

### `__bank(n)` variables and functions

cc45 puts a `__bank(n)` variable in the text sub-segment `bank.n` and a
`__bank(n)` function's code in `far.n` (#69). Every object's `bank.n`
chunks make one **data overlay** `bankN` (`bank4`, `bank5`, `bank800`, …;
64 KB at most), kept in bank `n` and never run: its symbols are their far
addresses, which only a 32-bit relocation (`R_LINEAR32`: cc45's hidden
`.dword _x`) may use; a 16-bit one is a link error (`'_x' is kept in bank 4
(__bank): ... refers to it by a 16-bit address`). The `far.n` chunks are
packed like `far` ones into overlays `bankNfar1`, … kept in bank `n`.
An overlay with a bank goes in a part of `--overlay-store` in that bank, or
in the whole bank when no range has it; the files, their loading by
`__ovl_init` and attic RAM's staging are as for other overlays (each bank a
file of its own). Data overlays do not count for the region's size (a
program with banked variables only has none), get no stubs, and are listed
in the map as `__bank variables, never run` (per object: `BANK` lines).

`examples/c/overlays` is a complete program (`make OVERLAY_MAP=1` for mapped overlays). `examples/c/mapped_overlays` checks mapped overlays at work: through MAP and through DMA, it shows that each overlay runs from its own place in bank 5, with no copy. `src/test/test_xemu.sh` tests calls in every direction, recursion between two overlays, function pointers, disk I/O inside an overlay, copied and mapped, in both calling conventions.

## Calling-Convention Thunks

A cc45 object exports a marker, `cc45.mode_zp` (ZP convention, the default) or `cc45.mode_stack` (`-fno-zpcall`); each function's attribute record has `FUNC_FLAG_ZP_CONV` when it takes ZP parameters. For each JSR from a caller to a callee with an attribute record:

- caller and callee from objects with the same marker: no check (the caller already used the callee's convention). The callee's object is the one whose definition the link uses: a weak definition a strong one replaces does not count (#357: a weak C default replaced by a hand-written routine is bridged by that routine's convention);
- otherwise the caller's convention is its object's marker (or, for hand-written code without a marker, its own `FUNC_FLAG_ZP_CONV`), and a mismatch with the callee's convention — **in either direction** — needs a thunk.

Callees without an attribute record (e.g. hand-written routines without `.func_flags`/clobber directives) are never checked.

By default each mismatch is reported and bridged:

```
ln45: warning: calling convention mismatch: '_main' calls '_add' (zp_call -> stack_call) (generating thunk)
```

The call is redirected to `__thunk_z2s_<callee>` (ZP caller → stack callee) or `__thunk_s2z_<callee>` (stack caller → ZP callee), one per callee, appended to the text segment. Their code (ZP parameter block at `$10`, `paramSize` from the callee's attribute record):

```asm
__thunk_z2s_foo:            ; ZP caller -> stack callee
    lda $10+n-1 / pha ...   ; push the ZP parameters, highest byte first
    lda $10 / pha
    jsr foo
    sta $0e                 ; (only if n > 0) keep A
    pla ...                 ; drop n bytes (works with the 16-bit stack)
    lda $0e
    rts

__thunk_s2z_foo:            ; stack caller -> ZP callee
    tsx / tsy / stx $08 / sty $09     ; pointer to the stack
    ldy #3 / lda ($08),y / sta $10    ; copy each argument byte, past the return address
    ...
    jmp foo                 ; foo's RTS returns to the original caller
```

With `--no-thunks` every mismatch is an error:

```
ln45: link error: calling convention mismatch: '_main' calls '_add' (zp_call -> stack_call)
```

`c45_stack.lib` needs no thunks: its hand-written assembly functions (`memcpy`, `strlen`, `putchar`, `malloc`, …) are ZP-convention and are declared `__fastcall__` in the headers, so stack-convention callers (the library's own C code and programs) call them with the ZP convention. A stack-mode object records such calls with a `cc45.zpcall.<callee>` marker (a weak absolute symbol), and the convention check treats those calls as ZP calls. Programs that declare a library function themselves without `__fastcall__` still get a (working) thunk.

## Error Messages

| Message | Cause |
|---------|-------|
| `ln45: no input files` | No object file on the command line |
| `ln45: cannot open X` / `cannot find library X` | Missing object, or library not found as given, in `CC45_LIB` or `-L` |
| `undefined symbol '_foo' (referenced in X)` | An import with no definition |
| `'x' is weak in X, whose code was assembled with its value there ($12), but the program defines it as $3456 (Y)` | A weak absolute symbol (ca45 `.weak x` / `x = value`) that X's code uses is defined with another value elsewhere (X would keep using its own); declare it `.extern` in X and define the default in another object, or remove the other definition |
| `duplicate symbol '_foo' (defined in X and Y)` | Two strong definitions |
| `calling convention mismatch: ...` | A mismatch with `--no-thunks` |
| `error: '_f' uses static allocation but is recursive (...)` | A SAC function on a call cycle (possibly across modules) |
| `error: '_f' uses static allocation but is reachable from ISR handler (...)` | A SAC function called (directly or indirectly) from an `__interrupt` function |
| `'_f' (code overlay o) is reachable from the overlay loader (__ovl_init -> ... -> _f), which runs before main, when no overlay is loaded; keep it resident` | Something the overlay loader calls at start-up (with `--pack-overlays` the unpacker, `__unpack`) is defined by the program in a code overlay (#346) |
| `relocation offset N out of range in X` / `relocation patch overflows segment in X` | A relocation points past its segment |
| `invalid symbol index N in X` | An external relocation names a non-existent import |
| `ln45: error: program ends at $XXXX, above the CPU stack top $BFFF (...)` | The program (BSS + base page) overlaps the 16-bit stack |
| `ln45: error: program ends at $XXXX, above the end of bank 0's RAM $BFFF (...)` | A C program reaches `$C000`, which reads as ROM (also with `-fno-stack16`); `--ram-top` for a program that maps RAM there |
| `ln45: error: the CPU stack top $XXXX is above the end of bank 0's RAM $BFFF (...)` | `-fstack-top` / `#pragma cc45 stack_top` at `$C000` or above |

Link errors are printed as `ln45: link error: <message>`; several convention/SAC errors are printed together.

Warning `ln45: warning: base-page storage: _f needs N bytes of the base page that functions active together with it use; calls to _f[, _g] save and restore the bytes they share`: the [base-page blocks](#base-page-blocks) of functions active together do not fit; those calls go through save/restore wrappers (`cc45 -fno-zp-locals` avoids it).

## Diagnostics

| Warning | Meaning |
|---------|---------|
| `ln45: warning: calling convention mismatch: ... (generating thunk)` | See above |
| `ln45: warning: unused global symbol 'X' (defined in FILE)` | Only with `-v`. An exported symbol no object imports. `_main`, names starting with `__`, `cc45.*` markers, `_f__ar` and linker symbols are not reported; other compiler-generated exports such as `_f__sac` and `_f__param_x` are, so expect many of these with cc45 objects |
| `warning: symbols 'X' and 'Y' overlap at $NNNN (different segments)` | Two symbols of different segments got the same address. cc45 objects export weak absolute constants (`cc45.mode_zp` = 1, `__zp_scratch` = 8, ...), so these can appear harmlessly |
| `ln45: warning: only N bytes left for the CPU stack ...` | Less than 512 bytes between the program end and `__stack_top` |

### Logging

By default `ln45` prints only errors, the warnings above and the `Linked ...` summary. `-v` adds, on stderr as `[ln45:INFO] …`, the cross-module analysis summaries and the `SAC overlay: ...` summary, and enables the informational warnings (`unused global symbol` — mostly library internals and globals used only in their own object); `-vv` adds the call graph (`[ln45:DEBUG] call graph: ...`) and the layout (`base-page block: _f at $80 ...`, `SAC overlay: place ...`); `-vvv` the relocation records and patches (`[ln45:DEEP] External reloc: ...`, `DATA relocation at offset ...`). The format and levels are the toolchain's (`include/Logger.hpp`; cc45 and ca45 log the same way).

## Function Metadata

Each function export can carry an attribute record (the base-page masks as address ranges, #360) (see [lib45 §4.3](../architecture/lib45.md#43-function-attribute-record-optional)) written by ca45 from `.func_flags`, `.zp_uses`, `.zp_clobbers`, `.zp_release`, `.reg_clobbers` and `.flag_clobbers` inside a `proc`. cc45 emits these for every function. The linker uses the convention, SAC and ISR flags, the parameter size (thunks) and the clobber masks (transitive clobbers in the map).

## Map File Format

`-M <file>` writes:

```
Linker Map
==========

Memory Layout
-------------
  TEXT   $200D - $4917  (10507 bytes)
  DATA   $4918 - $495E  (71 bytes)
  BSS    $495F - $4BFF  (673 bytes)

Object Files
------------
  main.o45
    TEXT  $2086 - $2143  (190 bytes)
    DATA  $4918 - $491D  (6 bytes)
    BSS   $495F - $496A  (12 bytes)
  math.o45
    TEXT  $2144 - $21B2  (111 bytes)
    BSS   $496B - $4976  (12 bytes)
  c45.lib(crt0_zp.o45)
    TEXT  $200D - $2085  (121 bytes)
  ...

Symbols (by address)
--------------------
  $0001  cc45.mode_zp                   main.o45 [weak]
  $200D  __init                         c45.lib(crt0_zp.o45)
  $2067  _init_features                 c45.lib(crt0_zp.o45) [weak]
  $2086  _main                          main.o45  [uses:- clob:- rel:- regs:AXYZ]
  $4460  _putchar                       c45.lib(asm_putchar.o45)  [uses:10-11 clob:10-11 rel:10-11 regs:AXYZ]
  $4B00  __zp_page                      <linker>
  ...

Call Graph
----------
  ___vformat_con_put -> _putchar
  ...

Source Lines
------------
  $2086  main.c:6
  ...
```

- **Memory Layout**: each non-empty segment. BSS includes the `__zp_page` (and `__zp_page_isr`) pages. A `SECT` line per section of `__section` variables (its range, bytes, variables). A ZP line appears only if objects have `.zp` segments, with their place in the program's base page.
- **Object Files**: every input object and pulled library member with its share of each segment (an object's text line spans its first chunk's position; sub-segment reordering can place parts elsewhere).
- **Symbols**: all global symbols with address, defining file (`<linker>` for linker symbols, empty for thunks) and `[weak]`. Functions with attribute records show `[uses: clob: rel: regs:]` (ZP masks printed as `$03`-based slot ranges) and, if calls add to them, `(trans: clob: regs:)`.
- **Call Graph**: caller → callees found through JSR relocations.
- **Source Lines**: first address of each `file:line` from the objects' line info.

With [code overlays](#code-overlays), these parts change:

```
Memory Layout
-------------
  TEXT   $200D - $4722  (10006 bytes)
  ...
  OVL    $AD00 - $AF37  (2 overlays, copied here by DMA when called)
    a              kept in bank 5 $0000 - $0237  (568 bytes)
    b              kept in bank 5 $0238 - $0452  (539 bytes)
    (file OVLTEST.OV1, 1109 bytes, loaded into bank 5 $0000 at start)

Object Files
------------
  ovl_a.o45  [overlay a]
    TEXT  $AD00 - $AF37  (568 bytes; kept in bank 5 $0000 - $0237)
    DATA  $472A - $472C  (3 bytes)

Symbols (by address)
--------------------
  $4611  _a_add                         ovl_a.o45  [uses:- clob:- rel:- regs:AX]  [stub: overlay a, $AD00]

Overlay Symbols
---------------
  overlay a (bank 5 $0000)
    $AD00  _a_add                         bank 5 $0000   ovl_a.o45  (stub $4611)
    $AD1A  _a_twice                       bank 5 $001A   ovl_a.o45  (stub $467A)

Overlay Lines
-------------
  overlay a (bank 5 $0000)
    $AD00  ovl_a.c:8
```

- **Memory Layout**: the `OVL` line gives where the overlays run: the
  region they are copied into, or the window MAP points at them
  (`--overlay-map`; mapped overlays each start on a page in far memory).
  Below it, where each overlay is kept: its bank, then the addresses in
  that bank.
- **Object Files**: an overlay object's text at the addresses it runs at,
  and where it is kept. Its data and BSS are resident (cc45 keeps
  `__noescape` constants in its code: [cc45](cc45.md#constants-kept-with-the-code-__noescape);
  ln45 refuses a reference to them from outside the overlay, and warns when
  their address is passed to a function that can call into another overlay,
  from cc45's `cc45.nesc.<caller>.<callee>` markers).
- **Symbols**: a function called from outside its overlay (or whose address
  is taken) is listed at its resident stub, tagged with its overlay and the
  address it runs at. Symbols used only inside an overlay are not in this
  list.
- **Overlay Symbols** and **Overlay Lines**: each overlay's symbols and source
  lines, listed per overlay because the overlays share run addresses. Each
  symbol shows the address it runs at, where it is kept, and its stub if it
  has one.

`objdump45 -d program.prg` picks up `program.map` automatically for symbolic disassembly.

## Debug File

`ln45 -g` (or `cc45 -g file.c -o prog.prg`) writes `prog.dbg` next to the program: its debug information for a debugger (#202), JSON, from the objects' line info and debug records (lib45.md 1.7, 1.12) at the program's final addresses: after library selection, dropped sections, overlays and the static-allocation overlay.

```json
{
  "format": "cc45-debug", "version": 1, "program": "prog.prg",
  "zp_page": 8960, "zp_page_isr": 8960,
  "overlays": [{"name": "primes", "runs_at": 44544}],
  "objects": ["main.o45", "c45.lib(zp_printf.o45)"],
  "files": ["src/main.c"],
  "lines": [[8487, 0, 16], [44544, 0, 30, "primes"]],
  "types": {"struct:pt": {"size": 7, "members": [{"name": "x", "offset": 0, "type": "u16"},
            {"name": "flag", "offset": 3, "bit": 0, "width": 1, "type": "u16"}]}},
  "functions": [{"name": "_add", "start": 8477, "end": 8520, "overlay": null, "object": 0}],
  "variables": [{"kind": "local", "scope": "_add", "name": "result", "type": "u16",
                 "location": {"zp": 48}, "object": 0}]
}
```

| Field | Meaning |
|-------|---------|
| `zp_page`, `zp_page_isr` | The program's base page and an interrupt handler's (`null` without crt0's) |
| `overlays` | The code overlays, in order, and the region they run at |
| `objects` | The linked objects; `object` fields index it |
| `files`, `lines` | The source files; `[address, file, line]` where a line's code starts (`, "overlay"` for an overlay's: they share addresses) |
| `types` | Struct and union layouts by `struct:NAME` / `union:NAME`; members with `offset` (and `bit`, `width` for a bit-field) and a type descriptor (lib45.md 1.12). A layout of a name another object already gave differently is `NAME@object`, and that object's types name it so |
| `functions` | Each function's code `[start, end)`, its overlay (`null`: resident) and object; static functions too (their labels, `_f__file`) |
| `symbols` | The program's global symbols and their addresses (`__exit`, `__stack_top`, labels; not the `cc45.*` markers) |
| `variables` | `kind` (`global`, `static`, `local`, `param`), `scope` (the function's label, `null` for a file's), C `name`, `type`, `location` and `object`. A location is `{"addr": N}` (memory), `{"zp": N}` (byte N of the base page: `zp_page`, or `zp_page_isr` in an interrupt handler), `{"frame": N}` (from the frame pointer at `$FD/$FE`), `{"reg": "AX"}`, or `null` (optimised away, or in a dropped section). A function's variables are left out when ln45 dropped the function |

A local in static storage shares it with others its function never has live together, and the static-allocation overlay gives functions never active at the same time the same bytes: such a location holds the variable while its function runs and it is live. `objdump45 -d prog.prg` uses `prog.dbg` for function names and source lines when there is no `prog.map`.

## Limitations

- The `.o45` format has four segments. ca45 maps `code`, `text`, `init` and any other named segment to TEXT (named sub-segments are kept as `OPT_SEGATTR` records and ordered as described above); only `data`, `bss` and `zp` map to DATA, BSS and ZP.
